# INV-14: X12 850 / 855 / 856 / 810 / 997 mappers, golden files and a loopback test partner

Owner: Eli. Branch: `inv-14/x12` (on top of INV-12, which is on main). Ticket: INV-14 on the Invintel board.

## What it does

- **Pure mappers** between our canonical documents and X12, no database and no clock (`x12.ts`, `x12-maps.ts`):
  - 850 purchase order <-> `CanonicalOrder` (BEG 00 original / 05 replace, CUR, DTM 002, NTE, N1 BY/SE, PO1 + PID, CTT, AMT TT)
  - 855 acknowledgment <-> `CanonicalOrderResponse` (BAK AD / AC / RJ, per-line ACK IA / IC / IR with a promised date)
  - 856 ship notice <-> `CanonicalShipNotice` (BSN, shipment / order / item hierarchy, TD5 carrier, REF CN tracking)
  - 810 invoice <-> `CanonicalInvoice` (BIG, CUR, ITD due date or net days, IT1 + PID, TDS in cents, TXI tax)
  - 997 functional acknowledgment <-> `CanonicalFunctionalAck` (AK1, AK2, AK5 with error codes, AK9)
- **Envelope.** ISA (fixed width, 106 characters) / GS / ST ... SE / GE / IEA, 004010 and 005010, test or production indicator, control numbers from an atomic counter per partner (wraps after 999999999). One transaction set per interchange.
- **The `x12` bridge.** Sends the 850 for a purchase order (the order dialog says "Send as X12 (850)"), reads what comes back, and on arrival: matches a 997 to the document we sent (by control number) and records a functional acknowledgment, records a 855 as the business answer on the order (accepted / accepted with changes / rejected), attaches 856 and 810 to the purchase order, turns an 810 into a captured invoice, and sends a 997 for everything it received. A partner's own settings (ids, version, transport, unit map, secret, receipts) are checked when saved.
- **Loopback test partner** (Documents > a sent order > "Let it answer"): receipt and accept, accept with changes, reject, refuse as malformed (997 with a segment count error), ship notice, invoice. Its documents go through the same acceptance as outside ones. Test partners on the loopback transport only.
- **Golden files** (`apps/api/src/golden/x12/`, fictional companies: Northwind Corrugated Co. / Sunrise Paper Mill): 850, 855 accepted / changed / rejected, 856, 810, 997 accepted / rejected. Each is also read back to the same canonical document.

## How to try it

`pnpm --filter @invintel/api seed:demo`, sign in, **Purchasing > PO-0002 (Lakeshore Film & Resin) > Send as X12 (850)**, then **Documents**, open the sent order, pick a scenario, "Let it answer". The order's dialog shows the supplier's answer, **Incoming invoices** shows an invoice sent as an 810.

## Decisions I made

- **Strict, not forgiving.** Writers refuse what X12 can't carry exactly and list every problem; readers refuse what they can't read exactly. No truncated part numbers, no guessed units, no rounded prices. The one exception: item descriptions (PID) are cut to 80 characters and cleaned, because they are only for people.
- **Test and live can never mix.** ISA15 must match the partner's mode in both directions, and the sender and receiver ids must be the partner's and ours. The test partner refuses to run for live partners.
- **One set per interchange.** Simple control numbers (ISA13 = GS06, ST02 = 0001), and a file with more than one set is refused instead of half read.
- **Canonical stays ours.** The 850 maps from `CanonicalOrder`, the same document the email bridge renders as a PDF; nothing in purchasing knows about X12.
- **A receipt for everything.** We return a 997 for each document received (switchable per partner) and never a 997 for a 997.
- **Answers are information.** An 855 or 856 is recorded and shown on the order; a person still changes the order or receives the goods. An 810 becomes a captured invoice, not a payable.
- **Unknown unit = no send.** A built-in table of common units (EA, RL, KG, ...) plus a per-partner map; no code, no document.

## Things I could not verify (read these before a real partner)

- The X12 standard is licensed and I worked from public partner guides, so segment layouts are the **common core, not certified conformance**. A real partner will have its own implementation guide (required segments, qualifiers, code lists); expect a profile per partner. Specific points to check against a guide: DTM qualifier 067 (current schedule delivery) for promised dates in ACK, REF*CN for the tracking number, TD5 carrier as free text in TD505 (many partners want a SCAC code in TD503), N1 loops without ids, BEG04 left empty.
- Not covered: 860 (changes), 820 (payment advice), 846 (inventory), 997 for several sets, 999, TA1, repeated PO1 sub-loops (SCH, SAC, taxes on lines), prices with more than two decimals, more than one order per ship notice, Z-lists of units. A revision (BEG 05) reads back as "revision 2" because X12 doesn't number them.
- No network transport: AS2 (signed, encrypted, MDN receipts), SFTP or a provider would be a transport adapter; nothing in the mappers changes.
- A document refused at the envelope (bad counts, wrong ids) gets a plain refusal over HTTP and is not stored; a real partner expects a 997 saying why. Add that when a real transport exists (the receipt builder already supports the error codes).
