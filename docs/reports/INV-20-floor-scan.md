# INV-20: floor speed (multi-scan documents, GS1-128 labels)

Owner: Eli. Branch: `inv-20/floor-scan` (on main with INV-18). Scope per Gus: (1) multi-scan flows: scan the destination once, then items (each +1, quantity prompt only when needed), one document at the end with undo and a clear running list; the same for receiving a PO delivery with many lines; (2) GS1-128 label parsing at receive (SSCC 00, GTIN 01, lot 10, expiry 17, quantity 37/30) with check digits, FNC1 handling, malformed labels rejected, pre-filling item, lot, expiry and quantity from one scan; check the rules against the GS1 General Specifications as publicly documented and say what was and wasn't verified. Reuse the Code 128 scanner and the lot, hold and unit rules.

## What it does

- **Receive and Move are multi-scan documents** (`pages/floor/receive.tsx`, `move.tsx`). Scan the place once; each item scan adds one (a counted item) or the label's count; same item + lot + expiry + pallet (+ source place for a move) is one line; +/- and tap-to-type per line, remove, **Undo last scan** (50 steps); items measured with decimals (kg, m, l) open a quantity prompt instead of adding one. One button posts the list as one document; one Undo takes it all back.
- **Move** picks the source place by itself when the item is in one place outside the destination, asks ("Take from where?") when it is in several, never offers the quality hold area, and refuses a quantity above what is there (including what is already on the list).
- **Receive a PO** (`receive-po.tsx`, new tile): pick the open order or type its number, scan the place once, scan the truck against the order's lines (progress, over-receipt flagged, items not on the order refused, a second lot or expiry of one item refused with the way out, **All arrived**), one receipt through the existing PO receive, one undo.
- **API**: `POST /receipts/batch`, `POST /moves/batch`, `POST /batches/:id/undo`. Everything is checked first (items exist, none tracked by unit, places valid, not the hold area, enough stock for the whole document), and if a line still fails or the database throws, the lines already posted are taken back, so a document is all or nothing. Lines of one document share a `batchId` on their ledger entries. Undo takes the whole batch under the existing rule (own entries within 15 minutes, or admin), refuses with the reason if the stock has since been used (nothing half-undone) or if any line went on quality hold. The undo logic was lifted out of the Activity route into `reverseGroup` (claim, put stock back, record) and the existing route now uses it. PO receipts get a `batchId` too, so a delivery undoes as one.
- **Rules reused**: lots (`supplierLot` per line), quality hold (`inspect` puts each line on its own NCR with its lot; such a batch isn't undoable from the floor, as before), units (a roll or unit-tracked item hands off to the existing roll flow and the list is kept), receive into the hold area refused as before.
- **Expiry** is new on the receipt line (`expiresOn`, YYYY-MM-DD): single receipts, batch lines and PO receipt lines accept it; Activity entries carry it and the "possible sources" lines in a trace show it. It is a date on the ledger entry, not an inventory rule (no FEFO, no expiry alerts: that would be its own item).
- **Pallet (SSCC)** is kept on the receipt line (`sscc`, validated) and written into the entry's reason ("Received: DN-4411 · pallet …").
- **Camera**: `CameraScanner` has a `continuous` mode for these screens (stays open, same code ignored for 2.5 s, Done button, shows the last code).

## GS1 parsing (`packages/shared/src/gs1.ts`)

Reads `]C1` / `]d2` / `]Q3` symbology identifiers, GS (0x1D) separators, printed `(01)...(10)...` brackets, and a bare string. Elements: 00, 01, 02, 03, 10, 11-13, 15-17, 20, 21, 22, 240-243, 250, 251, 254, 30, 37, 310n-369n (measures), 400-403, 410-417, 420, 422, 8004, 90-99. Per element: fixed or variable length with maximum, digits only or GS1 character set 82, mod-10 check digits for 00/01/02/03/402/410-417, real dates for 11-17 (day 00 = last day of the month, reported as such), the same AI twice, a count given both as 30 and 37, a zero count. Anything unknown, cut short, damaged or inconsistent is **refused with a reason**; nothing is repaired. `scanKind` decides what a scan is: a marked label that reads, a marked label that doesn't (shown as an error, never looked up as a SKU), a bare string that reads in full and starts with an SSCC or GTIN (used as a label only when nothing in the system has that exact code), or a plain code.

### What I verified against what is public

- **Verified in this work (public sources, fetched):**
  - The GS1 Barcode Syntax Resource's syntax dictionary (Apache-2.0, published by GS1): the list of AIs, their formats (N/X, fixed or variable, maximum lengths) and which are predefined-length (no separator after them): 00, 01, 02, 03, 11-17, 20, 31xx-36xx, 41x. My element table follows it.
  - Day `00` = "last day of the month" and that day 00 is not valid in a plain YYMMDD for some product classes: from a third-party library's summary of the General Specifications and GS1 change notice 21-040 (healthcare). I allow 00 for any product and say so on the line ("expires 2027-02-28"); I did **not** read the General Specifications text itself, so the healthcare restriction (and any per-AI exception) isn't enforced.
  - The GS1 character set 82 (digits, upper and lower case letters and `!"%&'()*+,-./:;<=>?_`): written from memory and checked by counting to 82; not re-read from the specification.
- **ZXing behaviour (what our wasm fallback does), tested here with the real decoder:** with the text mode the app uses (`Plain`), a Code 128 symbol containing a group-separator character comes back with a real ASCII 29 in the text; the symbology identifier is reported separately and is **not** in the text the app receives. So from the camera a GS1-128 label arrives without a leading `]C1` and with ASCII 29 between variable fields; that is exactly the "bare" and "separator" paths. Not tested: a real GS1-128 symbol (the writer in this ZXing build has no FNC1 character, so I could not produce one), the native Chrome `BarcodeDetector` (its handling of FNC1 is not documented in what I could fetch and may differ per device), or any physical scanner.
- **From memory, not verified against the text:** the century rule for two-digit years (I pick the century that puts the year within 49 years back and 50 years ahead of today; the General Specifications section 7.12 has the exact wording and I could not retrieve it), the full 31xx-36xx grid (I accept `3[1-6]` + any digit + decimal digit 0-5, which is broader than the specification's actual list), and the maximum label length (I only cap the scan at 120 characters).
- **Not read:** the General Specifications themselves (the public site's single page is too large to fetch here). **For someone with the PDF, check these against `packages/shared/src/gs1.ts`** (the AI table at the top of the file is the one place to correct):
  1. **Section 3, "GS1 Application Identifiers"**: for each AI in our table (00, 01, 02, 03, 10, 11-13, 15-17, 20-22, 240-243, 250, 251, 254, 30, 37, 31nn-36nn, 400-403, 410-417, 420, 422, 8004, 90-99): format, minimum and maximum length, and which AIs carry a check digit (we check 00, 01, 02, 03, 402, 410-417). Section 3.2 (the 31nn-36nn measure grid: which third and fourth digits exist) and 3.6.1 (character set 82).
  2. **Section 5.4.8.3, "Element strings with predefined length"** (the list of AIs that need no separator after them) and the GS1-128 rules for FNC1 in section 5 (a separator after a variable-length field unless it is last; the length cap on a symbol).
  3. **Section 7.9 / 7.12**: the date rules (YYMMDD, day 00 meaning the last day of the month, and which product classes it is not allowed for) and **7.12 "Determination of century in dates"** (we use the century that puts the year within 49 years back and 50 years ahead of today).
  4. **Section 7.9.1 and the check digit calculation** (mod 10, weights 3 and 1 from the right) for GTIN, SSCC and GLN.
  Section numbers are from memory of the General Specifications' layout and may differ by release; the topics are what to look for.

## Things you should know

- **A scanner that drops the group separator** (many keyboard-wedge scanners can't type ASCII 29 into a text field) turns `...10LOT7<GS>37 24` into `...10LOT737 24`. The lot then swallows the digits after it: not detectable from the data (a lot may legitimately contain digits). It is caught when the swallowed lot passes 20 characters ("may be missing a separator") but not otherwise, and the lot and count are shown on the line, so the person sees them. Set the scanner to send `]C1` and ASCII 29, or the bracketed form. Labels with the variable field **last** read correctly with no separator at all.
- **A GTIN-14 with a packaging indicator digit** (cases of an each) won't match an item that stores the each's barcode; the lookup tolerates zero padding only. The error offers to add the code as a new item. Multiple pack levels per item are a data-model change, not done here.
- The label's **count (37/30) only fills the quantity for items counted in whole units**; for weighed items the prompt asks.
- **Move ignores label counts** (a label on a pallet saying 24 doesn't mean you're moving 24).
- The demo's RSC-1296 barcode had a wrong GTIN check digit; labels for it would have been refused. I corrected it in my scratch database only; `seed-demo.ts` still has it (it is only a demo barcode).
- Not exercised: the **camera in continuous mode** on a phone (the pane has no camera; compiled and reviewed only) and a real handheld scanner. Everything else below was exercised.
