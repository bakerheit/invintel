## 2. How to look at it (about 10 minutes)

```bash
cd ~/workspace/invintel
docker compose up -d                      # MongoDB (already running if you use it daily)
pnpm install
MONGODB_DB=invintel_demo pnpm --filter @invintel/api seed:demo     # a demo corrugated plant, in its own database
MONGODB_DB=invintel_demo pnpm dev                                  # api :3001, web :5173
```

Open http://localhost:5173 and sign in as `demo@invintel.local` (the demo password is at the top of `apps/api/src/seed-demo.ts`). It is a separate database, so your real `invintel` data is untouched. To use your own data instead, run `pnpm dev` without `MONGODB_DB`: every change here only adds fields and collections, nothing is migrated or removed.

Suggested walk, in this order:

1. **Overview** (landing). Items out of stock or low, units waiting in Receiving, stock by kind of place, latest activity.
2. **Cmd-K** (or the Search button): type "kraft", then Enter. You land on the item's own page: where it sits, value, history.
3. **Purchasing**: the "Running low" card suggests quantities. Pick the supplier, draft an order, open it, place it, then receive part of it. Go to **Activity**, reverse that receipt, and watch the order's received count drop.
4. **Counts**: start a count of the Chemical room in **Floor mode > Count** (scan `CHEM`, then item SKUs and a number), then open **Counts** on the desk, see the differences, and post.
5. **Production** (desk): the released work order and its variance. Then **Floor mode > Production** (phone-sized window is best): Load material, report usage with a remnant, report output. Back on the desk, the variance moves.
6. **Floor mode > Receive / Move** with a roll or pallet item (rolls and pallets carry their own label), then **Labels** to see the printable sheet.
7. **Inventory > Import**: drop in a CSV (Export gives you the format). It previews every row before anything is written.
8. **Settings**: Features (switch Purchasing/Production off and watch them disappear), Members (promote someone), then **Audit log** to see all of it recorded and verify the chain.

## 3. What each piece does, and the decisions made

### Overview (Gus)
The landing page (`/o/:orgId`) answers "what needs attention?" in one API call. **Decision:** the item list moved to `/inventory` so the landing page can be a dashboard rather than a table. A **getting-started** card (add items, set up locations, receive stock, invite the team) shows for new organizations and hides when done or dismissed, because an empty org used to say "Nothing to chase", which is the wrong message on day one.

### Audit log (Will)
Every change (items, locations, organization, members, stock, and now suppliers, orders, work orders) is an append-only event with who, when and a before/after diff. Events are hash-chained (each stores a SHA-256 of itself plus the event before it), so editing or removing one is detectable; the Audit page has *Verify integrity* and *Export CSV*. **Honest limit:** tamper-evident, not tamper-proof. Someone with database write access could rewrite the whole chain, and truncating only the newest events can't be seen from inside the chain, so record the head hash somewhere outside the system now and then.

### People (Gus)
Settings > Members: the owner can make a member an admin and back; admins can remove members; the owner can remove admins; anyone can leave; the owner can't be demoted or removed. **Decision:** only the owner changes roles, and ownership isn't transferable yet. That is the safest rule that still lets you delegate; say if you want admins to be able to promote.

### Production (Eli)
Work centers (a machine, tied to a *production* location), **versioned BOMs** (inputs per output with scrap % and a yield %; a new version retires the old one, and a work order snapshots the version it was made from), work orders (planned > released > running > done, cancel), and three floor actions that post to the ledger: **Load** (stock to the machine), **Report usage** (used, scrap, or a remnant back to a location of your choice) and **Report output** (good units to stock, scrapped output booked in and out). Each action is one document: its ledger lines share a group id, so reversing it in Activity undoes all of it.
- **Variance:** expected (BOM x output reported, with scrap) against actual (used + scrap), per work order and a worst-first summary. Actuals are *derived from the ledger*, so reversed lines drop out automatically.
- **Variance approval:** set a threshold (percent, off by default); done work orders over it show "Needs approval", and an admin approves with a note (audited, atomic).
- **Scan:** on the floor tile you can scan a work-order number or a machine code instead of picking from a list.
- **Work centers** can be renamed and switched off (refused while it has released or running orders).
- **Decision (Eli):** a BOM expects output loss through `yieldPct`, and planned requirements already include it.

### Purchasing (Gus)
Suppliers and purchase orders. "Running low" lists items at or under their reorder level and suggests enough to get back to **twice the reorder level**, minus what is already on open orders (that rule is mine; change it if your buyers think differently). Orders go draft > ordered > partly received > received; admins write, place and cancel, **any member can receive** (the dock does that). Receiving puts stock into a location you choose through the ledger and ties the receipt to the order; **what has arrived is read from the ledger**, so reversing a receipt in Activity takes it off the order. Over-shipments are allowed and flagged. "Close short" finishes a partly received order. A short receive lease stops a cancel from racing a receive.

### Counts (Gus)
Cycle counts for one place at a time. Anyone counts (on the floor you scan the shelf, then each item, then type how many; the screen never shows what the system expects). An admin opens the count on the desk, sees System says / Counted / Difference / Value (largest money differences first), can fix a number, and **posts** it: each difference becomes an ordinary "Count CNT-0003" adjustment in the ledger, reversible in Activity. Uncounted items can be left alone or treated as zero. **Decisions:** blind counting, one open count per place, admins post (the "variance is a feature" idea from the research).

### Import and export (Gus)
Export writes one row per item and location. Import reads common spreadsheet headers (Part number, Qty, UPC, Bin...), previews every row (new, skipped, error with the reason) and writes nothing until you confirm. **Decisions:** it only ever *creates* (an existing SKU is skipped, never overwritten, so running the same file twice can't double stock); opening stock goes through the ledger as receipts; one bad row blocks the whole file so nothing half-loads; 1000 rows per file. Exported text that starts with `=`, `+`, `-` or `@` gets a leading apostrophe so a spreadsheet can't run it as a formula.

### Item page, Cmd-K, Features switch (Gus)
Every item has its own page (where it is, value, barcodes, recent ledger, links to history and audit). Ctrl/Cmd-K searches pages, items (by name, SKU or any barcode) and locations. Settings > Features hides Purchasing and Production for shops that don't use them, and the API answers 403 for them while they are off. Nothing is deleted; turning one back on restores it.

### Rolls and pallets, and labels (Will)
Some stock isn't a pile of identical things: a paper roll has a weight that shrinks as it's used, and you need to know *which* roll is where. An item set to **By roll or pallet** makes every physical roll its own **unit** with a label code (`U-000123`, or a pre-printed one), lot, remaining quantity, location and status. Floor **Receive** asks how much is on each, how many arrived and the lot, and offers *Print these labels*. **Move** is scan the roll, scan the place. **Look up** on a label lets you take some off it; at zero it is consumed. Everything writes ledger lines that carry the unit, updates the per-location stock, and is audited. **Labels** (sidebar) prints Code 128 or QR labels for items, locations and units at a few sizes. **Decisions (Will):** a location's stock for a unit item is always the sum of its units; a label can't equal any SKU or barcode; unit items refuse plain quantity receipts/moves/adjustments so nobody can bypass the units; tracking can't be switched while an item has stock. Eli then wired units into production: Load a scanned roll to the machine, report usage with the roll's remaining weight and send the remnant back with its new quantity.
**Not built (Will's cut list):** counting rolls by label (plan: scan labels, flag missing and misplaced units, post as unit adjustments in one group), reversing a unit's ledger entry in Activity (refused with a message), quarantine controls (the status exists, no UI), "in transit" units before arrival, a test on a real label printer (print layout only checked on screen), camera scan of roll labels (shared scanner, not re-tested). **Labels** is a Tools item and is not behind Settings > Features.

## 5. Known gaps and risks (be skeptical of these)

- **Whole-number quantities only.** No units of measure and no fractional weights (kg of a roll, MSF of board). A real roll-weight workflow needs this. It is the first thing I would build next.
- **No offline mode.** The floor needs the network. Plant wifi dead zones will hurt.
- **Not security-reviewed by Frida and not deployed.** Auth is solid for local use (argon2, httpOnly sessions, rate limits) but nothing here has gone through the pre-internet checklist.
- **No database transactions.** The ledger and the audit log are written right after the change, not in one transaction. Failures are logged for manual recovery. Closing that gap means running MongoDB as a replica set.
- **Production is single-step.** No routings, multi-step operations, co-products, scheduling or capacity.
- **Costing is just unit cost.** No FIFO/average costing, no landed cost.
- **Bundle is ~930 kB** (about 285 kB gzipped). Fine on a LAN, worth splitting later.
- **Email, Slack, push** and any other integration: none.
- `git push`: nothing has been pushed. `main` is ahead of `origin/main` by many commits.
